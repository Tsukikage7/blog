# 内容组织与发表规则

## 正式文章与技术笔记

正式文章完整解释一个工程问题：场景、不变量、失败路径、机制与取舍、可检查的例子、适用边界。技术笔记保存个人需要查阅的命令、配置和历史环境。只有关键内容未完成时才设草稿；删除或合并的旧正文不继续保存第二份草稿。

当前技术文章 19 篇，技术笔记 4 篇，文学作品 1 部、正文 10 章。文字为恢复的《我在练习不表演》十章；从删除前版本恢复，正文与原创建和更新时间均保留。剩余笔记为 Docker 历史安装、Kubernetes 历史安装、Compose 配置和 Git 命令备忘，不计入技术文章。

不要以篇数、字数或术语数量作为发表目标。不得补写未发生的项目经历、生产故障或未经运行的实验结果。模型实验、正确性验证、性能测试、生产验收必须分清。

## 分类与标签

正式文章每篇一个主分类，按文章解决的问题归类。目前为 Linux 与网络（9 篇）、并发编程（3 篇）、分布式系统（2 篇）、软件设计（1 篇）、数据工程（3 篇）、开发工具（1 篇）。不再使用「编程语言」作为分类：Go、Java、Scala 是实现技术，使用标签检索。算法、面试题与 MySQL 内容已按用户要求删除，不再保留这些分类或合集入口。

每篇一般使用 0–3 个标签，以具体技术或跨文章工程问题为准。统一 Go、Spark、Pekko、数据一致性等名称；标签不重复文章主分类。分类表明主要工程主题，标签帮助检索；两者不自动生成合集。

## 合集与文学作品

当前技术合集仅有 epoll，包含 8 篇正式文章。合集要求围绕同一主题、有明确的阅读顺序；独立的工程文章不为了数量强行串联。

文章、笔记和文字都使用相同的 series 与 seriesOrder 字段，序号必须唯一且为正整数。合集定义通过 kind 区分 technical 与 literary：技术合集接收文章及笔记，文学作品接收文字章节，类型混用会拒绝构建。未知合集、字段缺失和序号冲突会在构建时拒绝。目录从公开正文自动生成，不手工维护第二份章节清单。

## 历史内容与验证

原创建日期保留，实际改写时使用真实更新时间。历史环境明确版本与材料是否完整。删除路径通过 astro.config.mjs 直接指向有效目录；升级后的正文可保留原 URL。若原路径已经误导文章主题，改为对应当前选题的路径，并让旧文章与笔记地址直接跳转到最终正文。

独立例子位于 public/examples/content-completion。修改例子后同步正文、运行相关检查并重新生成下载包。编译产物、依赖缓存和删除主题的例子不得进入 public 或压缩包。

具体改写范围和验证边界见 [content-curation.md](./content-curation.md)，合集字段见 [series.md](./series.md)。

## 当前组织架构

保留现有 Astro 与 Markdown 内容集合，按阅读目的提供三种正文入口：

| 内容集合 | 用途                       | 列表组织               | 连续阅读                           |
| -------- | -------------------------- | ---------------------- | ---------------------------------- |
| blog     | 完整解释工程问题的技术文章 | 独立文章与技术合集入口 | 有阅读依赖时加入技术合集           |
| notes    | 命令、配置、环境记录与备忘 | 独立笔记列表           | 仅在确有顺序时加入合集             |
| writings | 小说、散文、随笔和诗歌     | 独立文章与作品入口     | 小说聚合为作品，目录按章节序号排列 |

内容类型决定入口与阅读页面；技术主题或文学体裁描述内容性质；标签提供跨内容的关键词检索；合集或作品定义顺序阅读。分类与标签不再占据顶级导航，也不把一本小说的书名作为标签来代替目录。

共享层负责公开内容筛选、规范 URL、合集定义与章节校验、搜索、统计和站点地图。seriesModel 已覆盖 writings，继续由章节元数据生成目录，不另建一份手工章节清单。展示层保留技术专题页与小说作品页各自需要的结构。

原章节地址保留，不因作品聚合改变已有链接。增加新的小说只需创建文学作品定义并给章节填写归属与顺序；独立散文、随笔不设置合集字段。
