原始问题是一次 Triple 泛化调用在客户端出现 `miss CallType in invocation`。这是一个特定实现版本中的调用契约缺失，不能推广成“Triple 协议根本不支持泛化调用”。要解决它，需要沿 Filter、Invoker、Codec 与服务端分派检查契约，而不只是消除 panic。

这篇保留原有开源贡献记录，并按可核对的 PR 状态重新整理：核心实现 [dubbo-go#3154](https://github.com/apache/dubbo-go/pull/3154) 于 2026-01-15 合入；早期方案 [#3077](https://github.com/apache/dubbo-go/pull/3077) 已关闭但未合入；示例 [dubbo-go-samples#1016](https://github.com/apache/dubbo-go-samples/pull/1016) 于 2026-03-12 合入。不能把早期方案描述成已合入的前置功能。

## 问题属于哪条路径

讨论范围是 Triple、Non-IDL、Unary、泛化参数与 Hessian2 封装。IDL 的 Protobuf stub、流式调用与其他泛化编码方式有自己的契约，不能因为客户端看起来都调用 Invoke，就认为线上的数据格式相同。

泛化调用省去预生成的业务 stub，仍然需要知道目标接口、方法名、参数类型与服务配置。它没有消除类型契约，只是把一部分校验从编译期移动到运行期。网关要把“能指定任意方法”约束成允许访问的接口与方法集合。

## Filter 重建 Invocation 时必须保留语义

业务调用通常携带方法名、参数、Reply、attachments 与调用类型。Generic Filter 将其重写为 `$invoke` 后，Triple Invoker 仍需要知道它是 Unary，并按照预期布局提取请求参数与响应占位符。

原有改动的关键不是多塞几个字段，而是维持三条不变量：请求参数不能被 Reply 占位符截断；重建 Invocation 后调用类型不能丢失；协议所需的原始参数与业务参数必须描述同一次调用。

| 层次              | 必须检查的事实               | 错误表现                 |
| ----------------- | ---------------------------- | ------------------------ |
| 业务调用          | 方法、类型列表、值列表相符   | 选错重载或反射参数不匹配 |
| 泛化转换          | `$invoke` 的三项业务入参完整 | 参数缺失、错位           |
| Triple Invocation | Unary 与 Reply 位置明确      | panic 或错误的请求布局   |
| 请求编码          | 外层格式与声明的 codec 一致  | 对端无法解包             |
| 服务端分派        | 方法存在且类型可转换         | 明确错误，不执行错误方法 |
| 响应解码          | 正常结果、空值与错误都可区分 | 把失败或 nil 当成功对象  |

不能为了让泛化 Unary 能工作，就对所有缺失 CallType 的调用统一兜底为 Unary。流式调用被静默降格后会产生另一个协议错误。默认值应受已识别的泛化调用路径约束。

## 传输封装与对象编码是两个边界

HTTP/2 上的 Triple 消息封装并不意味着每个业务对象必须是生成的 proto.Message。Non-IDL 互操作路径可以在外层 wrapper 中携带对象编码结果；请求 wrapper 与响应 wrapper 的结构和解码目标不同。

```mermaid
flowchart LR
  A[方法与参数类型契约] --> B[Generic Filter]
  B --> C[Triple Invocation]
  C --> D[请求 Wrapper 与对象编码]
  D --> E[服务端分派]
  E --> F[响应 Wrapper 与状态]
  F --> G[客户端解码与业务校验]
```

定位失败时分别保存可脱敏的元数据：目标接口与方法、编码方式、请求类型数量、传输状态、响应封装类型和业务错误。不要把业务参数、完整响应或鉴权附件直接写进调试日志。

对象编码还需要区分 Java `long` 与 `java.lang.Long`、空值是否允许、POJO 类名与字段类型、容器元素类型，以及 map 解码后的动态结构。Go 端一个 int64 不能自动证明任意 Java 重载都能互操作。返回值也不保证总是 `map[string]any`，无条件类型断言可能把已经成功的 RPC 变成客户端 panic。

## 对称测试比单个成功调用更有价值

源码与示例 PR 提供历史改动依据。升级或接入新的服务时，下面这张矩阵需要在固定客户端与服务端版本上重新执行；它是验收要求，不是本文已经完成的跨语言测试报告。

| 维度     | 必须覆盖的用例                       | 期望                                 |
| -------- | ------------------------------------ | ------------------------------------ |
| 入参     | 零参数、多个参数、空值、POJO、容器   | 数量与类型完整，非法输入可解释地失败 |
| 出参     | 标量、POJO、容器、nil、业务异常      | 请求与响应路径分别验证               |
| 分派     | 不存在的方法、重载、大小写与参数宽度 | 不静默调用另一个方法                 |
| 编码     | 双端支持与不支持的 codec 组合        | 明确的兼容或拒绝结果                 |
| 生命周期 | deadline、取消、连接断开             | 调用按期限结束，无挂起等待           |
| 重试     | 响应丢失、请求可能已经执行           | 按业务幂等语义决定重试               |

使用两个版本号之外，还应记录准确 commit、IDL/Non-IDL 模式、服务接口配置、编码方式和运行命令。本文核对的核心 PR head 为 `27b78d1d4ea9c77888bc067cc989132aa9298781`，样例 PR head 为 `a425cf5062c946c332e5fe5ae0833c0421546b2c`；这些标识用来定位改动，不代表生产环境正在使用它们。

## deadline 与幂等不能靠协议名字推断

客户端为完整操作设置 deadline，并让 context 贯穿过滤与传输链。对端可能在响应到达前完成写入，即使客户端观察到超时，也不能推断业务没有执行。

读取接口的重试与创建订单的重试应分开。写入需要业务请求身份与目标端幂等约束，重试后回读终态；SDK 的 retry 次数不能代替业务协议。网关同时需要对接口、方法、参数大小和调用并发设置边界，否则泛化入口会扩大故障影响范围。

## 如何复现与怎样解读结果

从 [已合入的泛化调用样例](https://github.com/apache/dubbo-go-samples/pull/1016) 中固定样例 commit，按该版本模块的依赖与启动步骤运行客户端和服务端，再逐项加入矩阵用例。当前官方用法可参考 [Dubbo-Go 泛化调用文档](https://dubbo.apache.org/zh-cn/overview/mannual/golang-sdk/refer/generic/)，不能把旧版本 API 原样套到所有后续版本。

本次整理核对了 PR 状态与核心代码改动，没有启动 Java/Go 双端服务，也没有重新执行互操作矩阵，因此不宣称当前 SDK 的全部模式已经验证。原文中未固定版本的“完整客户端”、伪 Go 条件表达式、任意 Java 服务都支持以及未复现的成功响应已删除，避免让读者把演示当成验证证据。
